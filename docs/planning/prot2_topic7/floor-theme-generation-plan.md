# Topic 7 詳細プラン: マップ生成の強化

作成日: 2026-08-20

## 目的

Topic 7では、毎階が同じ印象になる状態を崩す。

部屋の数、大きさ、密度をフロアごとに変え、「今回は広い」「今回は入り組んでいる」と分かるようにする。同時に、フロアごとの生成方針を1箇所のデータへ集め、後からテーマを足せる形にする。

最低ラインは、複数階を遊んだ時に地形の違いが分かること、敵・アイテム・階段の配置が破綻しないこと、視認性とカメラが維持されることとする。

## 事前調査で分かった制約

プランを書く前に、現在の `dungeon-layout.js` のパラメータを差し替えて200シードずつ生成し、成立するかを実測した。以下はその結果であり、テーマの数値はここから逆算している。

生成の成否（200シード中、フォールバック層へ落ちた回数）:

| 生成条件 | フォールバック | 平均部屋数 |
| --- | --- | --- |
| 標準（現状: 6-7室 / 5-9×4-7 / 余白3） | 0 | 5.9 |
| 小部屋 3-5×3-4 / 余白1 | 4 | 9.6 |
| 小部屋 3-5×3-4 / 余白2 | 1 | 9.8 |
| 小部屋 3-5×3-4 / 余白3 | 0 | 9.8 |
| 小部屋 4-6×3-5 / 余白3 | 0 | 9.5 |
| 大部屋 15-19×9-12 + 通常2-3室 | 0 | 3.5 |
| 大部屋 19-22×11-14 + 通常2-3室 | 11 | 3.3 |

既存機能との相性（開始部屋と階段部屋を除き、条件を満たす部屋が1つ以上ある割合）:

| 生成条件 | 強敵配置 5×4 | イベント部屋 6×5 |
| --- | --- | --- |
| 標準（現状） | 200/200 | 147/200 |
| 小部屋 3-5×3-4 / 余白3 | 92/200 | 0/200 |
| 小部屋 4-6×3-5 / 余白3 | 195/200 | 86/200 |
| 大部屋 15-19×9-12 | 200/200 | 150/200 |
| 大部屋 19-22×11-14 | 189/200 | 130/200 |

ここから決まったこと:

- **部屋間の余白は3を維持する。** 余白を1や2に縮めると通路が掘れず、フォールバック層（2部屋の一本道）へ落ちる。現在の通路掘りは「部屋タイルに隣接するマスを通れない」制約があるため、部屋を詰めると経路がなくなる。
- **大部屋の上限は19×12程度。** 19-22×11-14にすると200シード中11回フォールバックする。
- **小部屋は3-5×3-4では狭すぎる。** 強敵の配置成功率が92/200まで落ち、Topic 4が定めた「200中150以上」の基準を割る。イベント部屋に至っては0/200で完全に機能しなくなる。4-6×3-5なら強敵195/200まで戻る。
- **イベント部屋の6×5という条件は、現状ですでに147/200（73.5%）しか満たせていない。** これはTopic 7以前からの状態だが、テーマを増やすとさらに悪化する。この機会に条件をデータへ出す。

## 現状理解

- フロア生成は `dungeon-layout.js` の `createBuilder()` にまとまっており、部屋数 `rng(6, 7)`、幅 `rng(5, 9)`、高さ `rng(4, 7)`、部屋間余白 `3` がすべてコード内の定数になっている。
- `buildFloorLayout()` は12回まで生成を試し、`floorLayoutIsValid()`（全床タイルが開始部屋から到達可能）を満たす候補を返す。全部失敗すると2部屋のフォールバック層になる。
- 部屋は必ず矩形で、`connectRooms()` が `cx` 順に並べて隣り合う部屋を順につなぐ。`addOptionalConnections()` が65%でループを1本足す。
- `chooseStartAndStairRooms()` が開始部屋をランダムに選び、部屋グラフ上の距離が最大距離の0.6倍以上の部屋から階段部屋を選ぶ。
- 視界は光線ではなく構造ベースである。`dungeon-visibility.js` は、プレイヤーが部屋にいれば部屋全体、通路にいれば通路タイル列の前後4マスを見せる。部屋と通路という区分が前提になっている。
- 通行判定は `isWalkable()` の `map[y][x] === "."` ひとつだけで、移動、ダッシュ、敵AI、投擲、杖、アイテム配置、報酬配置がすべてこれを見ている。
- イベント部屋の候補条件 `room.w >= 6 && room.h >= 5` が `dungeon-events.js` の中に直書きされている。
- 強敵の部屋条件は、Topic 4で `minRoomW` / `minRoomH` として遭遇テーブルへ出してある。
- 暗闇の色は `floorDarknessTint()` が階層番号で3段階に分けている。フロアテーマに相当する唯一の既存要素である。
- ミニマップは `state.map` をそのまま縮小描画しているため、部屋の形が変わっても追従する。
- Topic 5とTopic 6で「カタログ（データ）＋システム（挙動）＋テーブル（配分）」の三層構成が確立している。

## スコープ

- `dungeon-layout.js` を、生成パラメータを外から受け取る形へ変える。
- テーマ「標準」「大広間」「小部屋群」を実装する。
- 階段位置ルールをテーマごとに調整できるようにする。
- 敵とアイテムの出現数にテーマ係数をかけられるようにする。
- イベント部屋の部屋サイズ条件をデータへ出す。
- 暗闇の色味と到着時の短いログをテーマから出す。
- 特定フロアをテーマ固定にできるようにする。
- デバッグクエリでテーマを指定できるようにする。
- フロアテーマのユニットテストと、テーマ別の生成健全性テストを追加する。
- README、手動テストチェックリスト、ロードマップ、完了メモを更新する。

## 非スコープ

- 水路と穴。理由は後述する。
- 迷路フロア。理由は後述する。
- 隠し部屋。発見操作、タイル状態、到達性判定の例外が必要になる。
- 矩形以外の部屋形状（L字、円形、柱のある部屋）。
- 部屋内の障害物。
- タイル画像そのものの差し替え。テーマの見分けは明暗と色味で出す。
- 高低差、ワープ、一方通行。
- フロアの広さ（`COLS` / `ROWS`）の変更。
- 経路探索を必要とする生成（現在の通路掘りをそのまま使う）。

### 水路と穴を入れない理由

`isWalkable()` は `map[y][x] === "."` の一択で、移動、ダッシュ、敵AIの `context.isWalkable`、投擲経路、杖の経路、アイテム配置、イベントオブジェクト配置、強敵報酬配置、視界の壁判定がすべてこれを見ている。

「通れないが見える」「通れるが落ちる」といった第3の通行区分を足すと、この全部を同時に直すことになる。Topic 6で倍速を見送ったのと同じ種類の変更で、地形の見た目を変える作業と混ぜると原因の切り分けができない。

### 迷路フロアを入れない理由

視界が部屋と通路の構造に依存している。迷路には部屋がないため、`roomAt()` も `addRoomVisibility()` も効かず、`chooseStartAndStairRooms()` も成立しない。さらに `corridorAt()` は毎ターン全通路の全タイルを線形探索しており、通路だけの迷路では負荷が跳ね上がる。

視界システムを光線方式へ作り替えるのが本筋で、それ自体が1トピック分ある。

代わりに「小部屋群」テーマで追加接続を増やせば、入り組んだ手触りはある程度近づけられる。まずそちらで体感を確かめる。

## 目標体験

- 階段を降りた瞬間に、今回のフロアの雰囲気が違うと分かる。
- 大広間では、部屋に入った瞬間に空間の広さと敵の数が見えて、突っ切るか壁沿いに回るかを考える。
- 小部屋群では、次の部屋に何があるか分からないまま、細かく進むことになる。
- 同じ標準フロアでも、階が深いほど暗く、色味が変わる。
- 到着時の短い一文で、フロアの性格が言葉でも分かる。
- テーマが変わっても、敵もアイテムも階段も普通に見つかる。

## 実装方針

### 三層構成

Topic 5、Topic 6と同じ形にそろえる。

- `floor-theme-catalog.js`: テーマ定義（データのみ）。
- `dungeon-theme-tables.js`: 階層ごとのテーマ配分（重み付き）。
- テーマの選択と既定値の補完は、`dungeon-layout.js` へ渡す前に `main.js` 側の薄い関数で行う。専用システムファイルを作るほどの処理量はない。

`dungeon-layout.js` は「テーマ」という概念を知らない。生成パラメータを受け取るだけにする。テーマ名で分岐を書き始めると、Topic 4で `encounterRank` を汎用化した意味が薄れる。

### テーマ定義

```js
{
  key: "greatHall",
  name: "大広間",
  arrivalText: "天井の高い、広い空間に出た。",
  generation: {
    rooms: { count: [3, 4], width: [5, 8], height: [4, 6], padding: 3 },
    featureRooms: { count: 1, width: [15, 19], height: [9, 12] },
    extraConnectionChance: 45,
    stairDistanceRatio: 0.5,
  },
  eventRoom: { minRoomW: 6, minRoomH: 5 },
  enemyCountScale: 1.15,
  itemCountScale: 1.2,
  darkness: null,
}
```

`featureRooms` は、通常部屋より先に配置する大きい部屋である。先に置くのは、狭い場所しか残っていない状態で大部屋を試すと失敗しやすいためである。実測では、この順で200シードすべて成立した。

`darkness` が `null` なら、現在の階層深度による色をそのまま使う。テーマ固有の色を持つ場合だけ上書きする。既存の「4F〜は紫系、7F〜は赤黒系」を壊さないためである。

### 生成パラメータの受け渡し

`createBuilder()` は既定値を持ち、`buildFloorLayout()` が呼び出しごとの上書きを受ける形にする。

```js
const layout = dungeonLayoutBuilder.buildFloorLayout({ generation: theme.generation });
```

既定値は現在のコードの定数をそのまま入れる。テーマを渡さない呼び出しは、今と同じ結果になる。

### テーマ配分

```js
window.GORO_DUNGEON_FLOOR_THEME_TABLES = [
  { minFloor: 1, maxFloor: 2, entries: [{ theme: "standard", weight: 100 }] },
  { minFloor: 3, maxFloor: 5, entries: [
      { theme: "standard", weight: 70 },
      { theme: "warren",   weight: 30 },
  ]},
  { minFloor: 6, maxFloor: 99, entries: [
      { theme: "standard",  weight: 55 },
      { theme: "greatHall", weight: 25 },
      { theme: "warren",    weight: 20 },
  ]},
];
```

1Fと2Fを標準固定にするのは、操作を覚える段階で地形の当たり外れを持ち込まないためである。Topic 3のイベント部屋、Topic 6の新しい敵も、浅い階を避ける方針で入れてある。

### 既存機能との衝突を避ける

事前調査の通り、テーマによっては強敵とイベント部屋の候補が減る。次の3つで対応する。

**1. 小部屋群の部屋サイズは4-6×3-5にする。** 3-5×3-4では強敵配置が92/200まで落ち、Topic 4のテスト基準を割る。4-6×3-5なら195/200で維持できる。

**2. イベント部屋の条件をデータへ出す。** `dungeon-events.js` に直書きされている `room.w >= 6 && room.h >= 5` を、Topic 4の `minRoomW` / `minRoomH` と同じ形でテーマ側から渡す。小部屋群では5×4へ下げる。

```js
// dungeon-events.js
return room.w >= (options.minRoomW || 6) && room.h >= (options.minRoomH || 5);
```

**3. 候補が無いフロアでは、イベント部屋も強敵も置かない。** これはTopic 3とTopic 4ですでにそうなっている。テーマを足しても、進行不能にはならない。

### 視認性とカメラ

受け入れ条件に「スクロールカメラと視認性が維持される」がある。大広間が唯一の危険箇所なので、先に条件を決める。

- 画面は640×480、タイル32pxなので、一度に見えるのは20×15マスである。
- 大部屋の上限を19×12にすると、横はほぼ画面幅、縦は画面内に収まる。部屋に入った瞬間に、ほぼ全体が視界に入る。
- `addRoomVisibility()` は部屋の全タイルと外周の壁を可視化する。19×12なら約270タイルで、現在の最大（9×7＝63）の4倍強になる。毎ターンの `Set` 構築が重くならないか実測する。
- ミニマップは `state.map` の縮小描画なので、部屋が大きくなっても表示は追従する。

`structure-tests.js` が持つ「開始部屋から他の部屋の内部が見えない」という検証は、部屋単位の可視化である以上、大部屋でも成立するはずである。テーマごとに同じ検証を回して確認する。

### 敵とアイテムの数

`placeEnemies()` と `placeItems()` が引く出現テーブルの `count` に、テーマ係数を掛ける。

```js
const count = Math.max(1, Math.round(rng(table.count[0], table.count[1]) * theme.enemyCountScale));
```

大広間は部屋数が平均3.5しかないため、候補部屋（`rooms.slice(1)`）が2〜3室になる。敵が大部屋へ集中しやすいが、部屋自体が広いので密度は上がらない見込みである。実測して、大部屋1室あたりの敵数が想定を超えるようなら係数を下げる。

小部屋群は部屋数が多いので係数1.0のままにする。1室あたり0〜1体になり、細切れに遭遇する形になる。

### 階段位置

`chooseStartAndStairRooms()` の `0.6` を `stairDistanceRatio` としてテーマから受ける。

- 標準: 0.6（現状維持）
- 大広間: 0.5（部屋が3〜4室しかないため、0.6では候補が消えやすい）
- 小部屋群: 0.7（部屋が多いので、もう少し歩かせる）

条件を満たす部屋が無い場合に開始部屋以外へフォールバックする既存の挙動は変えない。

### 到着表現

フロア遷移演出のカードに、テーマ名を出す。現在は `5F` と「さらに深く潜っていく……」の2行なので、後者をテーマの `arrivalText` に差し替える。テーマが標準の場合は現在の文言のままにする。

ログにも1行出す。Topic 3で挙がったまま実装していない「階層移動時の短いイベントテキスト」を、ここで最小の形で満たす。

### デバッグ

Topic 4で入れたローカル限定のデバッグクエリへ、テーマ指定を足す。

```
?debug=1&floor=8&theme=greatHall
```

テーマは毎階変わるため、Topic 4の5F固定のようにデータへ検証用の値を焼き込むより、クエリで指定できる方が確認しやすい。公開ホストでは無効のままにする。

## テーマ一覧

| キー | 表示名 | 部屋 | 特徴部屋 | 追加接続 | 階段距離 | 敵係数 | 出現 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `standard` | 石造りの回廊 | 6-7室 / 5-9×4-7 | なし | 65% | 0.6 | 1.0 | 全階 |
| `greatHall` | 大広間 | 3-4室 / 5-8×4-6 | 1室 / 15-19×9-12 | 45% | 0.5 | 1.15 | 6F〜 |

`standard` は現在の数値をそのまま写す。テーマ機構を入れても既存フロアが変わらないことを保証するための基準になる。

`warren` の追加接続を85%と高くしているのは、部屋が多い分ループがある方が迷いやすく、迷路に近い手触りが出るためである。

## テスト方針

### `tests/floor-theme-tests.js`

- テーマ配分テーブルの全 `theme` がカタログに存在する。
- 全テーマの重みが正の値である。
- 1Fと2Fが標準テーマ固定である。
- 全テーマの部屋サイズ下限が3以上である。3未満だと `doorwayForRoomToward()` の `clamp(target.cy, room.y + 1, room.y + room.h - 2)` が反転した範囲になる。
- 全テーマの部屋間余白が3以上である。事前調査の通り、縮めるとフォールバックが出る。
- 未知のテーマキーが標準へフォールバックする。

### `tests/structure-tests.js` の拡張

現在は単一の生成条件で50層を検証している。これをテーマごとに回す。

- 全テーマで200シード生成し、`floorLayoutIsValid()` が全件通る。
- 全テーマで、フォールバック層（2部屋1通路）へ落ちる割合が0である。
- 全テーマで、開始部屋から他の部屋の内部が見えない。
- 全テーマで、通路から部屋の内部が見えない。
- 全テーマで、すべての部屋に出入口がある。
- 標準テーマで、既存の「ループがときどきできる」「開始と階段が横方向の両端に固定されない」検証が引き続き通る。

### 既存機能との相性テスト

- 全テーマで、開始部屋と階段部屋を除いた5×4以上の部屋が200中150以上ある（Topic 4の基準）。
- 全テーマで、テーマ指定のイベント部屋条件を満たす部屋が200中100以上ある。

この2つは事前調査で使った測り方をそのままテストにする。テーマを足した時に、強敵とイベント部屋が静かに機能しなくなることを防ぐのが目的である。

### 既存テスト

`monster-system-tests.js`、`special-encounter-tests.js`、`item-system-tests.js`、`status-system-tests.js`、`monster-ai-tests.js` がすべて通ること。

### 実機に近い確認

Topic 5とTopic 6で使ったDOM差し替えの起動確認を再利用する。

- 各テーマで階を生成し、敵、アイテム、階段、イベントが配置される。
- 大広間で `computeVisibleTiles()` の所要時間が、標準フロアと比べて実用範囲に収まる。
- 大広間の1室あたりの敵数が想定を超えない。
- テーマをまたいで階段を降り続けても例外が出ない。
- ランダム操作の連続実行で例外が出ない。

### ブラウザ実機で見るもの

自動確認では分からないため、実機で見る。

- 大広間に入った瞬間の見え方とカメラの追従。
- 小部屋群でのミニマップの読みやすさ。
- テーマごとの色味の差が分かるか。
- フロア遷移カードのテーマ名が読めるか。

## 受け入れ条件

ロードマップの条件:

- 複数階を遊んだときに地形の違いが分かる。
- 敵、アイテム、階段の配置が破綻しない。
- スクロールカメラと視認性が維持される。

本プランで足す条件:

- テーマを渡さない生成が、Topic 7以前と同一の結果になる。
- 全テーマで200シード中フォールバック層が0件である。
- 全テーマで強敵の配置候補が200中150以上ある。
- テーマを追加する時に、`floor-theme-catalog.js` と `dungeon-theme-tables.js` の2ファイルだけで済む。
- `dungeon-layout.js` がテーマ名を知らない。
- 1Fと2Fの体感が変わっていない。
- イベント部屋の部屋サイズ条件がデータ側にある。
- デバッグクエリでテーマを指定して確認できる。
- 既存6テストと新規1テストが通る。

## 残す判断

- 水路と穴は入れない。通行判定の第3区分は、移動、AI、投擲、配置のすべてに波及する。地形の見た目を変える作業と同時にやると切り分けができない。
- 迷路フロアは入れない。構造ベースの視界が部屋と通路を前提にしているため、視界システムごと作り替える必要がある。小部屋群＋高い追加接続率で手触りを近似し、体感を先に確かめる。
- 隠し部屋は入れない。発見操作、タイル状態、到達性判定の例外が要る。
- 矩形以外の部屋形状は入れない。部屋を矩形として扱っている箇所（`roomContains`、`addRoomVisibility`、イベント部屋、強敵部屋、報酬配置）が多い。
- 部屋間の余白は3のまま動かさない。実測で、縮めると通路が掘れずフォールバックへ落ちることが分かっている。余白を縮めたい場合は、通路掘りの「部屋タイルに隣接するマスを通れない」制約から見直す必要がある。
- 大部屋の上限は19×12にする。それ以上は生成の失敗率が上がり、画面幅も超える。
- タイル画像は差し替えない。Topic 2で「大きな見た目改善は明暗差、照明、特殊部屋、階層テーマで検討する」と整理した方針に従う。
- テーマ固有のBGMは足さない。
- フロアの広さは変えない。`COLS` と `ROWS` を変えると、カメラ、ミニマップ、視界の前提が動く。

## 次Topicへの引継ぎ候補

- Topic 8のリザルト画面で、通ってきたフロアのテーマを戦績に出せる。
- 罠を実装する場合、テーマごとに罠の密度を変えられる。Topic 6の状態異常をそのまま付与元にできる。
- 視界を光線方式へ作り替えると、迷路フロアと水路が同時に現実的になる。どちらもそこが前提条件である。
- モンスターハウスは、テーマの一種（`enemyCountScale` を大きくした大広間）として表現できる可能性がある。ただし部屋単位の発火が必要なので、イベント部屋側の拡張になる。
- テーマごとの敵出現テーブルを持たせると、「大広間には群れで出る敵」といった配分ができる。バックログの `敵 / 群れで出る敵` と組み合わせられる。
