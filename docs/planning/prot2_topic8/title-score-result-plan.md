# Topic 8 詳細プラン: タイトル、スコア、リザルト

作成日: 2026-08-20

## 目的

Topic 8では、ゲームの入口と出口を作る。

今は `index.html` を開いた瞬間にダンジョンの1Fが始まり、全滅すると小さなパネルが出て `R` で最初からになる。遊びの中身はTopic 1からTopic 7でそろったが、「起動した」「終わった」「前回より良かった」という手触りがない。

最低ラインは、起動直後がタイトルとして成立すること、全滅後に今回の冒険を振り返れること、ベスト記録が残ることとする。

## 現状理解

- `main.js` の末尾で `generateFloor()` を呼び、そのまま `requestAnimationFrame(loop)` へ入る。タイトルもロード画面もない。
- 画面の状態を表す概念がない。`state.gameOver.active` と `state.menu.type` と `floorTransition.active` が、それぞれ独立に入力と描画を止めている。
- `loop()` は毎フレーム `updateAnimations()` → `draw()` → `updateUi()` を無条件で呼ぶ。
- `draw()` は必ずダンジョンを描く。ゲームオーバーはその上に重ねるパネルである。倒れた吾郎の演出が背後に見える作りになっており、これは残したい。
- 入力は `window.addEventListener("keydown")` の一本で、先頭から順に `dash` → `f2` → `m` → `r`（ゲームオーバー時）→ メニュー → 通常操作、と判定している。
- `canAcceptInput()` が `state.action` / `state.player.motion` / `state.gameOver.active` / メニュー / フロア遷移を見て、通常操作の可否を返している。
- 戦績は `state.stats` の `turns` / `defeated` / `strongDefeated` の3つだけ。ゲームオーバーパネルは、これに階層、レベル、経験値、武器、盾を足した8行を出している。
- `localStorage` はプロジェクト内で1箇所も使っていない。
- 音は初期ミュートで、`音 OFF` ボタンを押して初めて `AudioContext` を作る。ブラウザがユーザー操作を要求するための作りである。
- Topic 6で状態異常の死因（毒）が、Topic 7で `state.floorTheme` が入った。どちらも戦績に出せる材料である。
- 画像は `createImage()` → `resolveAssetUrl()` を通して読み、`drawSprite()` が失敗した場合は必ずCanvasの図形で代替している。タイル、敵、アイテムのすべてがこの形になっている。
- デバッグクエリ `?debug=1&floor=N&theme=X` はローカル実行時だけ有効で、指定した階から始められる。

## 目標体験

- ページを開くとタイトルが出て、「これは吾郎のゲームだ」と分かる。
- 何かキーを押せば始まる。迷わない。
- 操作を忘れたら、タイトルから説明を見られる。
- 倒れた瞬間は今まで通り、暗転と死因で締まる。
- そこから記録を見るか、すぐもう一度潜るかを選べる。
- 記録画面で、今回どこまで行ったか、何を倒したか、どんなフロアを通ったかを振り返れる。
- 前回までの自己ベストと並べて見えるので、次はもう少し先へ行きたくなる。
- タイトルで音をONにしておけば、最初から音が鳴る。

## 実装方針

### シーンの持ち方

タイトルを足すということは、「ダンジョンを遊んでいない状態」を初めて作るということである。ここが今回いちばん壊れやすい。

専用のシーン管理システムは作らない。`state` にフィールドを1つ足し、既存の3つの入口で分岐するだけにする。

```js
state.scene = "title"; // "title" | "help" | "playing" | "result"
```

分岐する場所は3箇所に限る。

1. `loop()` の描画: シーンに応じて `draw()` か `drawTitleScene()` か `drawResultScene()` を呼ぶ。
2. `updateUi()`: `playing` 以外ではHTML側のステータス更新を止める。
3. `keydown` ハンドラ: 先頭で `playing` 以外を振り分け、専用の入力処理へ渡す。

`canAcceptInput()` にも `state.scene !== "playing"` を足す。これで既存の移動、攻撃、メニュー、ダッシュが、タイトルやリザルトで暴発しなくなる。既存の3つの停止条件（ゲームオーバー、メニュー、フロア遷移）と同じ場所に足すだけで済む。

ゲームオーバーは今まで通り `playing` の中の重ねパネルのままにする。倒れた吾郎が背後に見える演出を壊さないためである。リザルトは、そこから明示的に進んだ先の別シーンとする。

### 画面遷移

```
起動
 └→ title ─(何かキー)→ playing
      ├─(H)→ help ─(Esc)→ title
      └─(S)→ 音のON/OFF切り替え（titleに留まる）

playing ─(HP0)→ gameOver重ねパネル（playingのまま）
                  ├─(R)→ playing（すぐ再挑戦）
                  └─(Enter)→ result
                                ├─(R)→ playing（再挑戦）
                                └─(Esc)→ title
```

死んだ直後に記録画面を挟まないのは、何度も潜り直す遊び方を邪魔しないためである。今の `R` 一発で再開できる速さは残す。

デバッグクエリが有効なとき（`?debug=1`）はタイトルを飛ばして `playing` から始める。階層やテーマを指定して確認する用途で、毎回タイトルを通るのは邪魔になる。

### 集計する戦績

既存の3つに加えて、次を `state.stats` へ足す。

| 項目 | 取り方 |
| --- | --- |
| `itemsUsed` | `useInventorySlot()` で実際に効果が発生したとき |
| `itemsPicked` | `pickUpItemAtPlayer()` の成功時 |
| `deepestFloor` | フロア生成時に `Math.max()` で更新 |
| `themesSeen` | フロア生成時にテーマキーを集合へ追加 |

`deepestFloor` を別に持つのは、将来ワープや帰還階段が入ったときに `state.floor` と食い違うためである。今は同じ値になる。

`itemsUsed` は「振ったが残り0だった杖」のような不発を数えない。Topic 6のレビューで、空の杖がターンを消費しない契約にしたので、そこと同じ基準にする。

死因は `state.gameOver.reason` にすでに入っている。Topic 6で毒用の文言が増えたので、リザルトにもそのまま出す。

### スコア

計算は説明できる形にする。プレイヤーが「何をすれば伸びるか」を読めることを優先する。

```js
score = deepestFloor      * 100
      + defeated          * 10
      + strongDefeated    * 50
      + level             * 20
      + exp;
```

ターン数は加点にも減点にもしない。少ないターンで進むのを評価すると、慎重に立ち回る遊び方が損になる。ターン数は情報として表示するだけにする。

5F到達、レベル3、撃破15、強敵1の場合でおよそ800点になる。桁が大きすぎず、伸びが分かる範囲に収まる。

### ベスト記録

`run-record.js` を新設し、スコア計算とベスト記録の更新を純粋関数として置く。DOMも `localStorage` も直接触らせない。保存領域は外から注入する。

```js
const recordSystem = window.GORO_DUNGEON_RUN_RECORD.createSystem({ storage: safeStorage });
recordSystem.scoreOf(runSummary);
recordSystem.load();
recordSystem.merge(runSummary);  // → { record, updatedFields: ["bestFloor", "bestScore"] }
```

保存する形:

```js
{
  version: 1,
  bestScore: 0,
  bestFloor: 0,
  bestDefeated: 0,
  bestStrongDefeated: 0,
  bestLevel: 0,
  bestAt: "",
  runCount: 0,
}
```

各項目は個別に最大値を取る。「最高スコアを出した回の撃破数」ではなく「これまでの最高撃破数」にする。理由は2つある。項目ごとの自己ベストの方が説明しやすいこと、そして更新されたときに「到達階層を更新した」と個別に演出できることである。

リザルト画面では、更新された項目に印を付ける。

### 保存が使えない場合

`localStorage` は次の場合に失敗する。

- Chromeで `file:` から開いた場合。README には「`index.html` をブラウザで開く」と書いてあり、実際に想定している遊び方である。
- プライベートウィンドウや、ストレージを無効にした設定。
- 容量超過。

読み書きは必ず包み、失敗しても例外を外へ出さない。

```js
const safeStorage = {
  read(key) {
    try { return window.localStorage.getItem(key); } catch { return null; }
  },
  write(key, value) {
    try { window.localStorage.setItem(key, value); return true; } catch { return false; }
  },
};
```

保存できない環境では、ベスト記録の欄に「この環境では記録を保存できません」と出し、それ以外は同じように遊べるようにする。**記録が保存できないことでゲームが遊べなくなる状態を作らない。**

読み込んだ値は必ず検証する。`version` が違う、数値でない、負の値、といった場合は初期値へ落とす。壊れた保存データで起動できなくなるのが、この手の機能でいちばん多い事故である。

### タイトル画面と音

今は初期ミュートで、`音 OFF` ボタンを押して初めて `AudioContext` を作っている。ブラウザが音の再生にユーザー操作を求めるためである。

タイトル画面は、この操作を自然に置ける場所になる。

- タイトルで `S` を押すと音のON/OFFが切り替わる。現在の状態を画面に出す。
- 音をONにしてから開始すれば、1Fの最初から音が鳴る。
- 既存の `音 OFF` ボタンはそのまま残す。ゲーム中に切り替えたい場合に使う。

初期状態はミュートのままにする。ページを開いた瞬間に音が鳴らない方が、公開ページとしては安全である。

### 操作説明画面

タイトルから `H` で開く静的なパネルにする。内容は README の「遊び方」から、操作に関する部分だけを抜き出す。

Topic 5、Topic 6で操作が増えている（`T` で投げる、杖を振る、状態異常）。ここで一度整理する。

スクロールは実装しない。1画面に収まる分量にまとめる。収まらない場合は、詳細をREADMEへ譲る。

### リザルト画面の内容

3つの区画に分ける。

**今回の結果**: 死因、到達階層、スコア、レベル、撃破数、強敵撃破数、使用アイテム数、拾得数、経過ターン、最終装備。

**通ったフロア**: Topic 7のテーマ名を並べる。「石造りの回廊 → 小部屋群 → 大広間」のように出す。地形の違いが記憶に残る作りにしたTopic 7の成果を、ここで回収する。

**自己ベスト**: 保存されている各項目と、今回更新した項目の印。保存できない環境ではその旨を出す。

## 生成画像の利用

タイトル画面とリザルト画面には、生成した画像を使ってよい。

> **方針変更（2026-08-20）**: Topic 2のSFC風は、ダンジョン内で常時並ぶタイル、敵、アイテム、吾郎スプライトの統一基準であり、タイトル／リザルトの一枚絵に対する絶対条件とはしない。UI用の一枚絵は、画面の役割に応じて写実、イラスト、ピクセルアートなどから選んでよい。今回は「吾郎がどういう人物かをプレイヤーへ示す」ことを優先し、タイトルとリザルトに本人資料を参照した映画的な写実表現を採用する。

### 使ってよい場所

- タイトル画面の背景。
- タイトルのロゴ（絵として作る場合）。
- リザルト画面の背景、または枠の装飾。
- ゲームオーバー時の一枚絵。

### 使わない場所

- ダンジョン内のタイル、壁、床、階段。
- 敵、アイテム、吾郎のスプライト。

これらはTopic 2で絵柄のルールを決め、Topic 5とTopic 6で追加した素材もその基準に合わせてある。同じゲームプレイ画面内へ異なる画風の生成画像を混ぜると、そろえた意味がなくなる。ゲーム画面の素材を変えるなら、それはTopic 2の続きとして別に扱う。一方、タイトルとリザルトはゲームプレイから独立したシーンなので、描画技法までゲーム内スプライトへ合わせる必要はない。

### 守ること

**画風**: SFC風は選択肢の一つであり、絶対条件にしない。タイトルでは冒険へ入る高揚感と吾郎本人の紹介、リザルトでは冒険後の疲労と再挑戦の余韻を優先し、写実表現を含めて最も効果的な画風を選ぶ。品質判断は、吾郎の人物像が伝わること、画面の物語と雰囲気が明確なこと、Canvasで重ねる文字の余白とコントラストが確保されていること、シーン遷移時に不自然なノイズを生まないことを基準にする。SFC風という理由だけで、UI用画像の写実化や将来のブラッシュアップを妨げない。

**解像度**: Canvasは640×480である。等倍で作るか、2倍の1280×960で作って縮小する。中途半端な解像度で作ると、拡大縮小でぼやける。

**形式とサイズ**: 既存はアイコンと敵がSVG、吾郎が WebP である。生成画像は WebP を基本とする。GitHub Pages で配るので、1枚あたり300KB程度を目安にする。タイトルとリザルトで合計1MBを超えないようにする。

**置き場所**: `assets/ui/` を新設する。`assets/ui/title_bg.webp` のように置く。

**読み込み経路**: 必ず `createImage()` を通す。`resolveAssetUrl()` が `window.GORO_DUNGEON_CONFIG.assetBaseUrl` を見て解決するため、これを経由しないとGitHub Pagesでパスが壊れる。

**フォールバックを必ず用意する**: `drawSprite()` が `false` を返したときに、画像なしでも成立する描画を書く。タイル、敵、アイテムはすべてそうなっている。タイトル画面が真っ黒になると、起動できていないように見えてしまう。**画像が1枚も読めなくても、タイトルとリザルトが読めて操作できる状態を保つ。**

**文字を画像へ焼き込まない**: ゲームタイトルのロゴを除き、メニュー項目、スコア、記録の数値はCanvasのテキストで描く。後から文言を変えたくなったときに、画像を作り直さずに済む。

**生成物の記録**: どの画像をどんな意図と指示で作ったかを、完了メモに残す。作り直すときは過去の画風を無条件に固定せず、人物の再現条件、構図、文字用の余白など、維持すべき要件と変更可能な表現を区別できるようにする。

### 段取り上の扱い

画像は最後に足す。先に、図形と文字だけで成立するタイトルとリザルトを作り切る。

理由は2つある。画像がなくても成立する状態がフォールバックそのものになること。そして、画面の配置が決まってから画像を作った方が、寸法の作り直しが減ることである。

## テスト方針

### `tests/run-record-tests.js`

スコア:

- 既知の入力に対してスコアが一致する。
- 到達階層0、撃破0でもスコアが負にならない。
- 欠けた項目があっても例外にならない。

ベスト記録の更新:

- 初回はすべての項目が記録される。
- 各項目が独立に最大値を取る。スコアが下回った回でも、到達階層だけ更新されることがある。
- 更新された項目名が返る。
- 何も更新されない回では、更新項目が空になる。
- `runCount` が毎回1増える。

保存データの検証:

- `version` が違う保存データは初期値へ落ちる。
- JSONとして壊れている保存データは初期値へ落ちる。
- 数値でない値、負の値は初期値へ落ちる。
- 想定外のキーが混ざっていても壊れない。

保存できない環境:

- `read()` が例外を投げる保存領域でも、初期値で動く。
- `write()` が失敗しても例外が外へ出ない。
- 書き込み失敗が呼び出し側へ伝わる。

- リザルトから `R` で再挑戦、`Esc` でタイトルへ戻る。
- タイトルとリザルトで、移動や持ち物の入力が暴発しない。
- 再挑戦時に戦績と状態異常と装備がすべて初期化される。
- 保存領域が例外を投げる状態でも、タイトルからリザルトまで通しで動く。
- ランダム操作の連続実行で例外が出ない。

### ブラウザ実機で見るもの

- タイトルの見た目と読みやすさ。
- 画像を外した状態でもタイトルが成立するか。
- リザルトの3区画が640×480に収まるか。
- 通過テーマの一覧が長い階層数でも溢れないか。
- タイトルで音をONにして開始したとき、1Fから音が鳴るか。
- `file:` で開いた場合と、ローカルサーバー経由で開いた場合の記録保存の違い。

## 受け入れ条件

ロードマップの条件:

- 起動直後にゲームタイトルとして成立する。
- 全滅後に今回の冒険を振り返れる。
- ベスト記録が残る。

本プランで足す条件:

- シーン分岐が `loop()`、`updateUi()`、`keydown`、`canAcceptInput()` の4箇所に収まっている。
- タイトルとリザルトで、ダンジョンの操作が一切効かない。
- 全滅から `R` 一発で再挑戦できる速さが保たれている。
- 保存が使えない環境でも、記録欄以外はすべて同じように動く。
- 壊れた保存データで起動が止まらない。
- 画像が1枚も読めない状態でも、タイトルとリザルトが読めて操作できる。
- 生成画像がゲームプレイ画面の素材と混ざらず、タイトル／リザルトでは各シーンの役割に適した画風を選べている。
- リザルトに、Topic 6の死因とTopic 7のテーマが出ている。
- 既存7テストと新規1テストが通る。

## 残す判断

- 中断セーブは入れない。ダンジョン全体の直列化が必要で、記録を残すこととは別の作業になる。
- ランキングと履歴は持たない。ベスト記録1件に絞る。項目ごとの自己ベストで十分に「次はもう少し」が生まれる。
- スコアにターン数を含めない。速さを評価すると、慎重に立ち回る遊び方が損になる。
- 死んだ直後にリザルトを挟まない。潜り直しの速さを優先する。
- タイトルの初期状態はミュートのままにする。公開ページとして安全側に倒す。
- 操作説明にスクロールを付けない。1画面に収まらない情報はREADMEへ譲る。
- ポーズメニュー、キーコンフィグ、音量設定はバックログのまま残す。UI/UXの項目として、まとめて別途扱う。
- 共有用テキストは入れない。`file:` でのクリップボード操作が環境によって動かないため、記録の形が安定してから検討する。
- 生成画像はタイトルとリザルトに限る。ゲームプレイ画面の素材はTopic 2の基準の下に置くが、独立したUIシーンの画風はその基準へ固定しない。
