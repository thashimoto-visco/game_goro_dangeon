# 吾郎の不思議なダンジョン リッチ化全体プラン

## 目的

現在のシンプルなローグライクを、スーパーファミコン時代の2D RPG/ローグライクに近い手触りへ段階的に強化する。

目標は「ただ画像を差し替える」ことではなく、ゲーム画面を見た瞬間の密度、入力後の反応、戦闘の気持ちよさ、アイテム選択の楽しさ、全滅時の余韻をまとめて底上げすること。

## 現状

- `main.js` にゲーム状態、マップ生成、戦闘、入力、描画がまとまっている。
- マップは矩形塗り、階段も単色矩形。
- プレイヤーとモンスターはSVG画像または簡易図形。
- 戦闘は移動先に敵がいると即座にダメージ計算される。
- アイテム、武器、装備、所持品の概念は未実装。
- 全滅時はログ表示と `R` キー再開のみ。
- `styles.css` で `image-rendering: pixelated` は設定済み。

## 目指す体験

- 画面全体がSFC風のタイルマップとして見える。
- プレイヤーとMOBが画面内で十分な存在感を持ち、カメラがプレイヤーを追ってマップをスクロールする。
- 吾郎が上下左右を向き、移動や攻撃に短いアニメーションがある。
- 攻撃時に斬撃、ヒットストップ、ダメージ数字、敵の点滅などが入る。
- 床にアイテムや武器が落ち、拾う・装備する・使う判断が生まれる。
- 全滅時に暗転、倒れ演出、戦績表示があり、リトライの流れが自然になる。
- UIがゲーム画面と調和し、HP、満腹度、装備、所持品、ログを読みやすく表示する。

## 開発方針

- 小さな段階で見た目と動作を確認できるようにする。
- 先に描画基盤と状態管理を整え、後続のアニメーションやアイテム追加を無理なく載せる。
- 既存のHTML/CSS/Canvas構成を維持し、必要になるまでビルドツールは導入しない。
- 最初はSVGまたはドット絵風の軽量アセットで進め、将来的にPNGスプライトシートへ差し替え可能にする。
- 1フェーズごとに「受け入れ条件」を明確にし、見た目と操作の両方を確認する。

## フェーズ構成

### Phase 1: 描画基盤とSFC風画面の土台

目的: 後続のリッチ化を載せるため、描画処理をレイヤー化し、タイル・キャラ・エフェクト・UIを分離する。

主な内容:

- 描画レイヤーの整理
- アセット定義の一元化
- タイル画像の導入準備
- プレイヤーの向き `direction` の追加
- アニメーション用の時間管理を追加
- 画面シェイク、フラッシュ、浮遊テキストなどのエフェクト枠を用意
- SFC風の画面トーンを決める

成果:

- 見た目を差し替えやすい描画構造になる。
- タイル、キャラ、エフェクトの描画順が明確になる。
- 攻撃モーションや全滅演出を実装する入口ができる。

詳細: `docs/planning/phase1-rendering-foundation-plan.md`

### Phase 2: スクロール画面とSFC風グラフィックス差し替え

目的: 画面を見た瞬間に「ゲームらしい」と感じるレベルまで、マップとキャラクターの見た目を強化する。まず全体マップ固定表示をやめ、キャラクターを大きく見せられるスクロールカメラを入れる。その上でタイル画像やUIを差し替える。

主な内容:

- マップサイズと表示サイズの分離
- プレイヤー追従カメラの追加
- プレイヤーとMOBの大型表示
- 足元基準の描画位置調整
- プレイヤー/MOBの描画順ソート
- プレイヤーの歩行モーション追加
- 床、壁、通路、階段のタイルアセット追加
- 床と壁のバリエーション表示
- プレイヤー4方向スプライトの導入
- モンスター画像の統一サイズ化
- アイテム用アイコンの仮追加
- UIパネルのドット絵風調整

受け入れ条件:

- 1フロアが画面より広く、プレイヤー移動に合わせて画面がスクロールする。
- プレイヤーとMOBが現在より大きく表示され、足元が現在マスに合っている。
- 単色矩形中心の画面から、タイルマップ画面に見た目が変わっている。
- プレイヤーが最後に入力した方向を向く。
- 敵、階段、床、壁の視認性がよい。
- 640x480のcanvas内で要素が重なったり潰れたりしない。

詳細: `docs/planning/phase2-sfc-graphics-plan.md`

### Phase 3: 攻撃モーションと戦闘演出

目的: 戦闘を即時処理から短い演出つきのターン処理へ強化する。

主な内容:

- 攻撃状態 `attack` の追加
- 隣接敵方向への移動入力を通常攻撃として扱う
- 通常攻撃は1ターン消費する
- Phase 3時点では専用攻撃ボタンを追加しない
- プレイヤー攻撃フレームの表示
- 斬撃または打撃エフェクト
- ヒットストップ
- ダメージ数字
- 敵の点滅、揺れ、ノックバック風演出
- 攻撃中の追加入力抑制

受け入れ条件:

- 敵に攻撃したとき、入力からダメージ確定まで短い視覚演出がある。
- 隣接敵の方向へ移動入力すると移動せず攻撃し、1ターン消費する。
- 演出中に状態が壊れない。
- 敵撃破時に消滅演出または点滅がある。
- 戦闘テンポが重くなりすぎない。

詳細: `docs/planning/phase3-combat-animation-plan.md`

### Phase 4: 持ち物・武器・床アイテム

目的: 探索中の判断材料を増やし、ローグライクらしい遊びを作る。

主な内容:

- `items` と床アイテム配置
- `inventory` と所持上限
- 武器、食料、回復薬の追加
- 武器装備による攻撃力補正
- アイテム拾得
- アイテム使用
- アイテム欄UI
- ログ文言の整理

受け入れ条件:

- 床アイテムを拾える。
- 所持品がUIに表示される。
- 武器を装備すると攻撃ダメージに反映される。
- 食料や回復薬を使える。
- 所持上限に達した場合の挙動が明確。

詳細: `docs/planning/phase4-inventory-items-plan.md`

### Phase 5: 全滅時の演出とリトライ導線

目的: ゲームオーバーを単なる停止ではなく、印象に残る締めにする。

主な内容:

- HP 0時の状態 `gameOver` 追加
- プレイヤー倒れ演出
- 赤フラッシュまたは画面シェイク
- 暗転オーバーレイ
- 到達階層、撃破数、経験値、経過ターンの表示
- `R` キー再挑戦UIの強化
- 入力受付状態の整理

受け入れ条件:

- HP 0時に画面が段階的にゲームオーバー表示へ遷移する。
- 戦績が表示される。
- `R` キーで状態が初期化され、演出状態も残らない。

### Phase 6: バランス、音、仕上げ

目的: リッチ化した見た目とゲーム内容を、遊びとしてまとまりのある状態へ磨く。

主な内容:

- 敵ステータスと階層スケーリングの調整
- アイテム出現率の調整
- 武器の強さとデメリット調整
- SE追加
- BGM追加
- 操作説明の更新
- README更新
- 軽量な手動テスト表の整備

受け入れ条件:

- 1Fから数階層を遊んで、戦闘・拾得・使用・全滅・再挑戦が自然につながる。
- 画面、UI、音の方向性が揃っている。
- READMEの遊び方と実装内容が実態と合っている。

## 技術的な分割案

現状は単一ファイルでも規模が小さいため、Phase 1ではまず関数分割を優先する。必要になったら後続フェーズでファイル分割する。

将来的な分割候補:

- `main.js`: 起動、ループ、入力の接続
- `state.js`: ゲーム状態、初期化
- `map.js`: マップ生成、歩行判定
- `combat.js`: 戦闘計算
- `assets.js`: 画像読み込み、スプライト定義
- `renderer.js`: canvas描画
- `effects.js`: エフェクト状態
- `items.js`: アイテム定義、所持品処理

ただし、ビルドなしでブラウザから直接開く運用を保つなら、ES Modules化やファイル分割は慎重に行う。最初は `main.js` 内で責務を分ける。

## アセット方針

### 短期

- 既存SVGを活かし、ドット絵風の簡易SVGまたは小さなスプライトシートを追加する。
- まず大型キャラとスクロールカメラの基準を固め、その後にタイルを少数のバリエーションから追加する。
- アニメーションは2から4フレームで十分とする。

### 中期

- プレイヤー、敵、エフェクトを同一解像度ルールに揃える。
- `assets/sprites/` と `assets/tiles/` のように用途別フォルダを作る。

### 長期

- PNGスプライトシート化を検討する。
- アセット一覧ドキュメントを作る。

## 手動確認項目

- `index.html` をブラウザで開ける。
- 画面が640x480のcanvas内に収まる。
- プレイヤー移動に合わせてカメラがスクロールする。
- プレイヤーとMOBの足元が現在マスに合っている。
- 矢印キー/WASDで移動できる。
- 敵に接触して攻撃できる。
- 階段で次階へ進める。
- HP 0でゲームオーバーになる。
- `R` キーで再挑戦できる。
- コンソールに画像読み込みエラーが出ない。

## リスクと対策

### リスク: アニメーション追加でターン処理が壊れる

対策:

- Phase 1で入力受付状態とアニメーション状態を分ける。
- 演出中は新しい移動入力を無視する。

### リスク: アセット座標のミスで表示が崩れる

対策:

- スプライト定義を一元化する。
- `drawImage` の切り出し座標を直接散らさない。

### リスク: スクロール化で座標系が混ざる

対策:

- ゲームロジックはグリッド座標、描画はワールド座標、canvas表示は画面座標として分ける。
- `worldToScreenX()` / `worldToScreenY()` のような変換関数を通して描画する。
- 歩行判定や戦闘判定にカメラ座標を持ち込まない。

### リスク: UIが狭くなり所持品表示が読みにくい

対策:

- Phase 4ではまず右パネル表示にする。
- canvas内UI化は後回しにする。

### リスク: ファイル分割でローカルHTML起動が複雑になる

対策:

- Phase 1では単一JS維持を基本とする。
- 分割する場合はREADMEに起動方法を明記する。

## 完了の定義

全体リッチ化の完了条件:

- スクロールするSFC風のタイルマップ、キャラクター、UIが揃っている。
- 攻撃モーションとヒット演出がある。
- アイテム、武器、装備、所持品が機能している。
- 全滅時に演出と戦績表示がある。
- READMEに最新の遊び方が書かれている。
- 主要操作を手動確認済み。
